omcp is an open source project that welcomes contributions from
anyone. You do not need permission to contribute — no sponsor to find, no working group to join,
no meeting to attend, and no chat server to be vetted in. Open a pull request.

## The submission bar

Every contribution is judged openly, in the pull request, against the same five requirements.
Nothing else.

<Steps>
  <Step title="It follows good coding practices">
    Readable, consistent with the surrounding code, and no gratuitous churn.
    Match the conventions already in the files you touch. Keep the diff scoped
    to the problem you are solving.
  </Step>
  <Step title="It solves a real problem">
    Something has to actually be broken, missing, or unworkable in production.
    Speculative abstractions and changes that exist only to be tidy are not
    problems.
  </Step>
  <Step title="The problem is clearly stated">
    Your pull request says, up front and in plain language: what the problem is,
    who hits it and under what conditions, and why the change addresses the
    cause rather than the symptom.
  </Step>
  <Step title="It ships independently verifiable unit tests">
    Working tests that exercise the change, pass on a clean checkout, and can be
    run by a stranger who clones your branch — **including the data they need to
    run**.
  </Step>
  <Step title="It documents itself">
    The author writes the chapter for the official reference documentation that
    covers the change, and ships it in the same pull request.
  </Step>
</Steps>

<Warning>
  The fourth requirement is not negotiable. A test that depends on data only you
  possess, on a live network service, or on a private endpoint is not
  independently verifiable. Fixtures, sample payloads, schemas, and example
  documents belong in the repository next to the tests that use them.
</Warning>

If the change is untestable as written, that is evidence the design needs revisiting — not grounds
for an exemption.

### The reference chapter

Whoever opens the pull request writes the documentation chapter for the change and ships it in the
same pull request. Not a changelog line and not a comment — the section a reader who has never
seen your feature would need in order to use it correctly: what it does, how to use it, and where
its edges are.

The author is the person who understands the change best at the moment it is written, which is why
the job is theirs. Documentation written later, by someone else, is documentation that does not get
written.

A change that alters observable behaviour and ships without its chapter is incomplete, the same way
it would be incomplete without its tests.

## Before you begin

### Prerequisites

- **[Git](https://git-scm.com/downloads)** - For cloning repositories and submitting changes
- **[Node.js 24+](https://nodejs.org/)** - Required for building and testing
- **npm** - Comes with Node.js, used for dependency management
- **[GitHub account](https://github.com/signup)** - For submitting pull requests and issues
- **Language-specific tooling** - If contributing to an SDK, the appropriate development
  environment for that language (e.g., Python, Rust, Go)

Verify your setup:

```bash
node --version  # Should be 24.x or higher
npm --version   # Should be 11.x or higher
git --version   # Any recent version
```

<Note>
  These commands work the same on macOS, Linux, and Windows, so you're good to
  go on any platform.
</Note>

### Repository structure

The omcp specification, documentation site, and proposals all live in
[`enclawed/omcp`](https://github.com/enclawed/omcp). Throughout this guide, **specification
repository** refers to that repo.

interoperate with it unchanged. They are maintained in their own repositories:

## Your first contribution

### Step 1: Set up your environment

<Steps>
<Step title="Fork the repository">

Click the **Fork** button on the [repository page](https://github.com/enclawed/omcp) to create your own copy.

</Step>
<Step title="Clone your fork">

```bash
git clone https://github.com/YOUR-USERNAME/omcp.git
cd omcp
```

Replace `YOUR-USERNAME` with your GitHub username.

</Step>
<Step title="Install dependencies">

```bash
npm install
```

This installs the tools needed for schema generation, documentation building, and validation.

</Step>
<Step title="Verify everything works">

```bash
npm run check
```

This runs TypeScript compilation, schema validation, example validation, documentation link checks, and formatting checks. If everything passes, your environment is good.

</Step>
</Steps>

If `npm run check` fails, see [Troubleshooting](#troubleshooting) below.

### Step 2: Find a real problem

Start from something that is actually broken or missing:

1. **Documentation defects** - typos, unclear explanations, broken links, incomplete examples
2. **Open issues** - bug reports in the
   [issue tracker](https://github.com/enclawed/omcp/issues) with reproducible steps
3. **Schema examples** - add examples to `schema/draft/examples/` where a primitive is hard to
   understand without one
4. **Something you hit yourself** - the best source. If the spec blocked you in production, that
   is a real problem, and you can state it precisely.

### Step 3: Make your change

<Steps>
<Step title="Create a branch">

```bash
git checkout -b fix/your-description
```

Use a descriptive branch name, like `fix/typo-in-tools-doc` or `feat/add-example-for-resources`.

</Step>
<Step title="Make your changes">

Edit the relevant files. If you're editing schema files, run `npm run generate:schema` to regenerate the JSON schema and documentation.

</Step>
<Step title="Write the tests, and commit the data they need">

Cover the failing case and the behaviour you claim to have fixed. Commit the fixtures alongside them, so the tests run on a clean checkout with no setup.

</Step>
<Step title="Run checks">

```bash
npm run check
```

Fix any issues before committing. `npm run format` auto-fixes most formatting errors.

</Step>
<Step title="Commit with a clear message">

```bash
git commit -m "Fix typo in tools documentation"
```

Describe what you changed and why. Reference issue numbers if applicable.

</Step>
</Steps>

### Step 4: Submit a pull request

<Steps>
<Step title="Push your branch">

```bash
git push origin fix/your-description
```

</Step>
<Step title="Open a PR on GitHub">

You can use the [GitHub CLI](https://cli.github.com/):

```bash
gh pr create --fill
```

Alternatively, navigate to your fork on GitHub and click **Compare & pull request**.

</Step>
<Step title="State the problem">

Write out what is broken, who hits it, and why your change fixes it. A reviewer measures the solution against the problem, so a PR without a stated problem cannot be reviewed on merit.

</Step>
<Step title="Show the tests passing">

Point at the tests and the command that runs them. Anybody reading should be able to reproduce your result from the branch alone.

</Step>
<Step title="Include the reference chapter">

Ship the documentation for your change in the same pull request, so the feature and the chapter that explains it land together.

</Step>
</Steps>

### What makes a good contribution

| Harder to review                             | Thoughtful and impactful                         |
| -------------------------------------------- | ------------------------------------------------ |
| Large PR with unrelated changes              | Focused PR addressing one problem                |
| Reformatting code without functional changes | Fixing a bug with a clear explanation            |
| Vague commit messages ("fixed stuff")        | Descriptive commits linking to issues            |
| Submitting with failing CI checks            | All CI tests pass before requesting review       |
| "Trust me, it works"                         | Tests a stranger can run, with the data included |
| Shipping a feature with no documentation     | The reference chapter written by its author      |
| Duplicating existing documentation           | Documenting an undocumented feature or edge case |

## Working with the specification repository

### Schema changes

The TypeScript schema (`schema/draft/schema.ts`) is the **source of truth** for the protocol. It
defines every message type, request/response structure, and primitive (tools, resources, prompts)
that clients and servers exchange. SDK implementers across all languages rely on this schema to
build conformant implementations.

When you run `npm run generate:schema`, it generates:

- The JSON schema (`schema/draft/schema.json`) for validation
- The Schema Reference documentation (`docs/specification/draft/schema.mdx`)

To modify the schema:

<Steps>
<Step title="Edit the TypeScript schema">

Make your changes in `schema/draft/schema.ts`.

</Step>
<Step title="Add examples">

Add JSON examples in `schema/draft/examples/[TypeName]/` (e.g., `Tool/my-example.json`). Reference them in the schema using `@example` + `@includeCode` JSDoc tags. These examples are validated by `npm run check`, so they double as committed test data.

</Step>
<Step title="Generate JSON schema and docs">

```bash
npm run generate:schema
```

</Step>
<Step title="Validate your changes">

```bash
npm run check
```

</Step>
</Steps>

<Warning>
  Wire compatibility matters. omcp stays drop-in compatible with the wider
  ecosystem, so a change that breaks existing clients or servers has to justify
  the break explicitly in the pull request and provide a migration path.
</Warning>

### Documentation changes

Docs are written in [MDX format](https://mdxjs.com/) (Markdown with JSX components) and powered by
[Mintlify](https://mintlify.com/). The `docs/` directory contains:

- `docs/docs/` - Guides and tutorials for getting started and building
- `docs/specification/` - Formal protocol specification (versioned by date)

<Steps>
<Step title="Start the local docs server">

```bash
npm run serve:docs
```

This launches a live preview at `http://localhost:3000` with hot reloading.

</Step>
<Step title="Make your changes">

Edit the relevant `.mdx` files. You can use [Mintlify components](https://www.mintlify.com/docs/components) like `<Note>`, `<Tip>`, `<Steps>`, and `<Card>` for richer formatting.

</Step>
<Step title="Check for issues">

```bash
npm run check:docs
```

This validates formatting, broken links, and other common issues.

</Step>
</Steps>

### Protocol changes

Substantial protocol changes are written up as a proposal file in the `seps/` directory and
submitted as a pull request, so the reasoning lives in version control next to the specification
it changes. See [Proposals](/community/sep-guidelines).

A proposal is a technical document, not an application. It needs no sponsor and no prior approval
to be opened.

<Steps>
  <Step title="Build a prototype first">
    Demonstrate the idea works before writing it up. What the prototype teaches
    you is the substance of the proposal.
  </Step>
  <Step title="State the problem it solves">
    Concretely, with the conditions that produce it.
  </Step>
  <Step title="Write the proposal">
    Follow the [proposal guidelines](/community/sep-guidelines).
  </Step>
  <Step title="Ship conformance tests and their data">
    A protocol change is verifiable or it is not a protocol change.
  </Step>
  <Step title="Write the reference chapter">
    The specification change and the documentation that explains it land in the
    same pull request.
  </Step>
</Steps>

## Contributing to an SDK

Each SDK has its own repository and contribution guidelines. Read the repository's own
`CONTRIBUTING.md` for environment setup, coding standards, and commit conventions — and write
tests with committed fixtures there too. Bug fixes should include a test that reproduces the
issue; new features should have tests covering the expected behaviour.

## Review

Review happens in the pull request, in public, in writing. A change is evaluated on whether it
meets the five requirements — not on who submitted it, and not on conversations held anywhere
that is not the pull request.

A submission that is rejected is rejected with a stated technical reason. Silence is not review,
and a closed pull request without a reason is a bug in the process.

## Getting help

- **[GitHub Discussions](https://github.com/enclawed/omcp/discussions)** - Exploration and
  conversation: questions, direction, and problems that need shaping before becoming concrete
  tasks
- **[GitHub Issues](https://github.com/enclawed/omcp/issues)** - Actionable work: bug reports
  with reproducible steps, documentation fixes, and well-defined tasks

If you're unsure whether something is ready to be an issue, start with a discussion. For the full
picture, see [Contributor Communication](/community/communication).

## Troubleshooting

### `npm run check` fails

Common causes:

- **Wrong Node.js version** - Ensure you have Node.js 24+
- **Missing dependencies** - Run `npm install` again
- **Schema out of sync** - Run `npm run generate:schema`
- **Formatting issues** - Run `npm run format` to auto-fix

### My tests pass locally but not for reviewers

Almost always missing data. Check that every fixture your tests read is committed, that no test
reaches a network service, and that nothing depends on environment variables or local
credentials. Clone your own branch into a fresh directory and run the tests there — if it fails,
that is exactly what a reviewer sees.

### My pull request has been sitting unnoticed

1. Ensure all CI checks pass
2. Confirm the PR states its problem clearly — an unstated problem is the most common reason a PR
   stalls
3. Politely ping a reviewer in a comment

### My change was rejected

A rejection comes with a stated technical reason. That reason is the thing to engage with:

1. **Address the feedback and resubmit** - Most rejections name a specific concern
2. **Try a different approach** - Same problem, different solution, informed by what you learned
3. **Split it up** - A large change is often several smaller ones, each independently verifiable

Rejection is not permanent, and it is not personal. What it is, always, is written down.

## Authorship

Authorship belongs to humans. The person who opens a pull request is its author, is accountable
for it, and is credited for it.

We do not ask which tools you used to get there, and there is nothing to disclose. A good idea is
a good idea regardless of what executed it, and work is judged on what it does — against the five
requirements above — not on how it was produced.

What you are accountable for is unchanged: you understand the change, you can explain why it is
needed, and you have verified it with tests anybody can re-run.
