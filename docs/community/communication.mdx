---
title: Contributor Communication
description: How discussion and decisions happen in the omcp project
---

Everything that shapes omcp happens **in writing, in public, on GitHub**.

There is no private channel where decisions are really made, no meeting you need an invitation
to, and no real-time chat you must be vetted into before your work is taken seriously. If a
discussion is not in a pull request, an issue, or a discussion thread, it did not happen.

## Channels

| Channel                                                                         | Purpose               | When to use                                      |
| ------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------ |
| [Pull requests](https://github.com/enclawed/omcp/pulls)                         | Proposing changes     | Any change to the spec, schema, tooling, or docs |
| [GitHub Discussions](https://github.com/enclawed/omcp/discussions)              | Structured discussion | Direction, longer-form debate, open questions    |
| [GitHub Issues](https://github.com/enclawed/omcp/issues)                        | Actionable tasks      | Bug reports, documentation fixes                 |
| [Vulnerability reports](https://github.com/enclawed/omcp/blob/main/SECURITY.md) | Security issues       | Vulnerabilities — **never post publicly**        |

All communication is governed by our
[Code of Conduct](https://github.com/enclawed/omcp/blob/main/CODE_OF_CONDUCT.md). We expect
respectful, professional, and inclusive interactions across all channels.

## Pull requests

The pull request is the primary venue. It is where a change is proposed, argued, revised, and
accepted or rejected — and the thread is the permanent record of why.

A pull request is read against the four requirements in
[Contributing](/community/contributing): good coding practices, a real and unaddressed problem, a clearly
stated problem, and working unit tests that anybody can verify independently, shipped with the
data they need to run.

Reviews address the code and the reasoning. A rejection comes with a stated technical reason.
Closing a pull request without one is a bug in the process, not an outcome.

## GitHub Discussions

Use for structured, long-form discussion where no specific change is on the table yet.

- Direction and milestone discussion
- Announcements and release communications
- Open questions and consensus-building
- Problem reports that need shaping before anyone writes code

If a repository doesn't have Discussions enabled, use GitHub Issues instead.

## GitHub Issues

Use for bug reports and actionable development tasks.

- Bug reports with reproducible steps
- Documentation improvements with specific scope
- CI/CD problems and infrastructure issues
- Release tasks

Protocol proposals are submitted as pull requests adding a file to the
[`seps/` directory](https://github.com/enclawed/omcp/tree/main/seps), not as issues. See
[Proposals](/community/sep-guidelines).

## Real-time chat

Chat is fine for saying hello. It is not where anything is decided.

No proposal gains standing from having been discussed in a chat server, and no contributor is
disadvantaged for never having joined one. If a conversation anywhere leads toward a decision
or a proposal, it moves to a pull request, issue, or discussion — with its reasoning written
out — before it counts for anything.

## Security issues

**Do not post security issues publicly.**

1. Use the private security reporting process in
   [SECURITY.md](https://github.com/enclawed/omcp/blob/main/SECURITY.md).
2. Follow responsible disclosure guidelines.

Private handling of an unpatched vulnerability protects users; it is the one narrow exception to
working in the open, and it ends at disclosure.

## Decision records

Decisions are documented where anyone can find them later:

| Type                  | Location                                                              |
| --------------------- | --------------------------------------------------------------------- |
| Technical decisions   | [Pull requests](https://github.com/enclawed/omcp/pulls) and proposals |
| Specification changes | [Changelog](/specification/draft/changelog)                           |
| Process changes       | [Community documentation](/community/contributing)                    |

When documenting decisions, we retain as much context as possible:

- Background context and motivation
- Options considered
- Rationale for the chosen approach
- Implementation steps
